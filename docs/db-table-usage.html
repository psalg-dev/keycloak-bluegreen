Keycloak DB table usage: what a blue/green copy has to carry

Reads and writes per table, from pg_stat_user_tables on the demo's two Postgres clusters (2026-11-11 21:05 UTC, default profile, k6 load). Click a category to filter the tables.

reads (table + index scans) writes (rows inserted + updated + deleted), in category color square-root scale

How to read it

  • blue: pg-1 (Keycloak 26.7.5): counters since the database was created, so schema install, config-cli, user seeding and load. Writes are skewed by the seeding.
  • green: pg-2 (Keycloak 26.8.1): counters since the copy, so mostly traffic, plus green's schema upgrade (27 changelog rows). Closer to a steady state. That the copy starts the counters at zero is assumed, not checked.
  • Reads are scan counts, not rows. Keycloak caches realms, clients and users in Infinispan, so config reads are understated.
  • Ephemeral (auth_session, root_auth_session, single_use_object): in-flight logins and one-time codes. Losing them costs a login retry.
  • Sessions: Keycloak 26 keeps online sessions in offline_*_session (offline_flag = '0'). Not copied = everyone logs in again.
  • Config is redeployable (config-cli, client sync) except component, which holds the realm signing keys: without them every issued token is invalid after the switch.
  • Audit: event_entity is empty here (login events are not stored in the DB in this setup); admin_event_entity has about one row per seeded user. Check eventsEnabled in production.
  • Tables with 0 rows but many scans (cluster_event, user_group_membership, revoked_token, broker_link) are polling or per-login lookups of unused features.
  • About 70 more tables are idle at 0 rows (organizations, authorization services, user federation, consents, workflows) and left out. The categories are assigned by hand, not derived from the data.
  • This is a demo load mix (2 logins/s, 60 s access tokens, so many refreshes). Production ratios will differ; the query below gives them.
select relname, n_live_tup, coalesce(seq_scan,0)+coalesce(idx_scan,0) as scans,
       n_tup_ins + n_tup_upd + n_tup_del as writes
from pg_stat_user_tables where schemaname = 'public' order by 4 desc, 3 desc;
